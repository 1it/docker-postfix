## v0.1.5

### Features

- **Use certificates issued outside the container** — `TLS_CERT_FILE` and `TLS_KEY_FILE` point Postfix at an existing certificate and key, whether it comes from an acme.sh or certbot client on the host, a commercial CA, or a mounted secret. Nothing about the built-in issuance changes: no port 80 is needed, and setting `LETSENCRYPT_EMAIL` alongside an external certificate logs that issuance is skipped.
- **External renewals apply without a restart** — the pair is compared by content every `TLS_WATCH_INTERVAL` seconds (default 300, `0` disables the check). On a change it is validated and published, and Postfix is reloaded. Files that are missing, unreadable, or invalid mid-renewal leave the previous certificate in service.
- **Certificates in the standard layout are reused** — `/etc/letsencrypt/live/<MAILNAME>/fullchain.pem` and `privkey.pem` are now used without any variables, which covers certificates placed there by an external client. When the container's own acme.sh state for that name matches the active certificate and key, it keeps renewing them through the existing renewal loop. Stale state that does not match is not allowed to replace the active pair.
- **Validation and readable copies** — an external pair is checked at startup and its subject, expiry date and chain length are logged, with a warning inside 7 days of expiry. Every certificate in the bundle is parsed, not just the first: a valid leaf followed by a malformed intermediate passes a first-certificate-only check and then fails TLS setup. The private key must hold exactly one key, matching the leaf; CRLF key markers are accepted. The pair is staged in a private directory under a restrictive umask, combined into one PEM with an explicit newline separator, and the assembled PEM is validated before activation. The published file is owned `root:postfix` with mode `0640`, and the two most recent pairs are kept.
- **Published through `smtpd_tls_chain_files`** — the key and certificate live in one file, which is what Postfix's documentation recommends for exactly this reason: with them in separate files, a process starting during a rollover can load a certificate that does not match the key. `smtpd_tls_cert_file` and `smtpd_tls_key_file` are cleared, since Postfix ignores them and warns while they are set.
- **Renewals detected from what is installed** — the watcher starts from the pair it actually published rather than from the source files, so a renewal that happens while the container is starting is installed instead of being recorded as already applied. Both fingerprints hash the same byte stream, the published key-then-chain, so an unchanged certificate is not republished and reloaded on every check.

### Bug Fixes

- **Existing in-container Let's Encrypt certificates kept a stale renewal command** — a volume created by an earlier image still stored `postfix reload` as its renewal command. Because an existing certificate is reused without issuing, nothing replaced it: a renewal updated the source files and reloaded Postfix, while the combined PEM Postfix actually reads was never refreshed, so the certificate expired silently. The install paths and the publisher are now re-registered on every startup, for both the RSA and EC state layouts. If registration fails, startup keeps serving a valid selected pair but warns and disables the automatic renewal loop rather than running a renewal hook that may not publish the new pair.
- **Re-registering cannot destroy a working certificate** — `--install-cert` rewrites its target files from acme.sh's state, so an incomplete state directory truncated the certificate to zero bytes. The files are backed up first and restored if registration leaves an unusable pair behind; the certificate in use is never at risk.
- **A stale published certificate is no longer served after a restart** — a combined PEM left on the persistent `postfix_certs` volume by a previous run, another `MAILNAME`, or an older version of the certificate is now replaced on startup instead of being served until some later renewal.
- **The self-signed fallback now takes effect** — `main.cf` lives in the container layer, so a restart that fell back to self-signed left `smtpd_tls_chain_files` pointing at the previous pair. Postfix prefers that parameter, so it kept serving the old certificate. The fallback clears it and restores the self-signed paths.
- **Explicit certificate paths override detection, not just issuance** — with both paths set but unusable, the container no longer falls through to a certificate found under `/etc/letsencrypt/live/`. Explicit paths select the certificate, so anything unusable there means the documented self-signed fallback.
- **Stale acme.sh state cannot take over an externally renewed certificate** — the managed renewal path is selected only when the stored acme.sh leaf certificate and private key match the active files. This avoids reinstalling a previous local certificate over a newer external certificate for the same hostname.
- **The renewal loop only renews the selected hostname and key variant** — `acme.sh --cron` checks every domain in its config directory, and their saved publisher hooks all target the same Postfix PEM. The loop now runs `acme.sh --renew` for only `MAILNAME` with its matched RSA/EC variant, so an old certificate for another hostname cannot replace the one Postfix serves. The normal “not due yet” result is handled without terminating the renewal loop.
- **PEM serialization handles valid edge cases** — key and fullchain files are separated with a newline even when a valid key lacks a final newline, and the combined PEM is parsed before activation. CRLF private-key markers are counted correctly rather than rejected as an empty key.
- **In-container Let's Encrypt no longer falls back to self-signed on first issuance** — the acme.sh `--reloadcmd` was `postfix reload`, and `postfix reload` fails when Postfix is not running yet. Since it runs during entrypoint startup, before the daemon starts, acme.sh treated the reload as a failed install, and the container discarded a valid certificate. Renewal now runs a small publisher instead, which applies the new pair and reloads only when Postfix is already running.

### Upgrade Notes

- `TLS_CERT_FILE` alone, without `TLS_KEY_FILE`, is ignored with a warning. The container then continues with Let's Encrypt issuance or the self-signed fallback.
- When both are set and the pair is unusable, the container falls back to self-signed. It does not fall through to Let's Encrypt issuance: explicit certificate paths override issuance whether or not the pair turned out to be valid, so a misconfigured mount cannot silently trigger an HTTP-01 challenge that needs port 80.
- A missing, unreadable, or invalid external pair falls back to self-signed certificates, matching the existing behaviour when Let's Encrypt issuance fails.
- Mounting external certificates: mount the root of the certificate tree rather than only `live/<domain>/`. In certbot's layout the files in `live/` are relative symlinks into `../../archive/`, and a mount of `live/` alone leaves the targets outside the container.
- Published pairs are written to `/etc/ssl/postfix/tls/live/tls.pem` instead of separate `fullchain.pem` and `privkey.pem` files. Any tooling that inspected the old paths should read the combined file; the contents are the same key followed by the certificate chain.
