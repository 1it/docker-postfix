## v0.1.5

### Features

- **Use certificates issued outside the container** — `TLS_CERT_FILE` and `TLS_KEY_FILE` point Postfix at an existing certificate and key, whether it comes from an acme.sh or certbot client on the host, a commercial CA, or a mounted secret. Nothing about the built-in issuance changes: no port 80 is needed, and setting `LETSENCRYPT_EMAIL` alongside an external certificate logs that issuance is skipped.
- **External renewals apply without a restart** — the pair is compared by content every `TLS_WATCH_INTERVAL` seconds (default 300, `0` disables the check). On a change it is validated, copied into `/etc/ssl/postfix/tls/`, and Postfix is reloaded. Files that are missing, unreadable, or invalid mid-renewal leave the previous certificate in service.
- **Certificates in the standard layout are reused** — `/etc/letsencrypt/live/<MAILNAME>/fullchain.pem` and `privkey.pem` are now used without any variables, which covers certificates placed there by an external client. When the container's own acme.sh state for that name is present, it keeps renewing them through the existing `acme.sh --cron` loop.
- **Validation and readable copies** — an external pair is checked at startup and its subject, expiry date and chain length are logged, with a warning inside 7 days of expiry. Every certificate in the bundle is parsed, not just the first: a valid leaf followed by a malformed intermediate passes a first-certificate-only check and then fails TLS setup. The private key must hold exactly one key, matching the leaf. The pair is staged in a private directory under a restrictive umask, combined into one PEM owned `root:postfix` with mode `0640`, and published by renaming a single symlink. The two most recent pairs are kept.
- **Published through `smtpd_tls_chain_files`** — the key and certificate live in one file, which is what Postfix's documentation recommends for exactly this reason: with them in separate files, a process starting during a rollover can load a certificate that does not match the key. `smtpd_tls_cert_file` and `smtpd_tls_key_file` are cleared, since Postfix ignores them and warns while they are set.
- **Renewals detected from what is installed** — the watcher starts from the pair it actually published rather than from the source files, so a renewal that happens while the container is starting is installed instead of being recorded as already applied.

### Bug Fixes

- **In-container Let's Encrypt no longer falls back to self-signed on first issuance** — the acme.sh `--reloadcmd` was `postfix reload`, and `postfix reload` fails when Postfix is not running yet. Since it runs during entrypoint startup, before the daemon starts, acme.sh treated the reload as a failed install, and the container discarded a valid certificate. Renewal now runs a small publisher instead, which applies the new pair and reloads only when Postfix is already running.

### Upgrade Notes

- `TLS_CERT_FILE` alone, without `TLS_KEY_FILE`, is ignored with a warning. The container then continues with Let's Encrypt issuance or the self-signed fallback.
- When both are set and the pair is unusable, the container falls back to self-signed. It does not fall through to Let's Encrypt issuance: explicit certificate paths override issuance whether or not the pair turned out to be valid, so a misconfigured mount cannot silently trigger an HTTP-01 challenge that needs port 80.
- A missing, unreadable, or invalid external pair falls back to self-signed certificates, matching the existing behaviour when Let's Encrypt issuance fails.
- Mounting external certificates: mount the root of the certificate tree rather than only `live/<domain>/`. In certbot's layout the files in `live/` are relative symlinks into `../../archive/`, and a mount of `live/` alone leaves the targets outside the container.
- Published pairs are written to `/etc/ssl/postfix/tls/live/tls.pem` instead of separate `fullchain.pem` and `privkey.pem` files. Any tooling that inspected the old paths should read the combined file; the contents are the same key followed by the certificate chain.
